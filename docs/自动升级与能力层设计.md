# 自动升级与能力层设计

## 背景

tuzi-switch 面向国内用户分发，既要尽量降低升级摩擦，也要避免把桌面应用降级成“远程脚本执行器”。这次改造把升级分成两条链路：

- 原生升级：Rust、Tauri 权限、插件、安装包变化，走 Tauri 官方 updater。
- 前端热更新：只更新 Vite/React 产物，走签名校验后的本地资源加载。

能力层 `Capability Facade v1` 为热更新前端提供稳定 native 能力，避免前端直接依赖大量零散 Tauri command。

## 核心原则

1. 不在 App 内执行 `curl | bash`。
2. 不直接从 CDN 加载远程 JS。
3. 所有下载资源必须校验 hash 与签名后再启用。
4. native 能力只追加，不破坏已有 capability 的语义。
5. 热更新前端必须先校验 `requiredCapabilities`，不满足就跳过更新。

## 原生升级链路

原生升级使用 Tauri 官方 updater：

- `createUpdaterArtifacts: true` 生成 updater 包和 `.sig`。
- `latest.json` 放在 `release-manifest` 分支，通过 jsDelivr 分发。
- 安装包和 updater 包仍放 GitHub Release Assets。
- 用户确认后由 Tauri updater 下载、验签、安装。

这样做的原因：

- Tauri updater 已经覆盖签名校验和平台安装细节。
- GitHub Release Assets 适合承载 `.dmg`、`.msi`、`.AppImage` 这类大文件。
- jsDelivr 更适合承载小型 manifest，不适合作为大安装包主存储。

## 前端热更新链路

前端热更新只覆盖 `dist` 资源，不覆盖 Rust/native 能力。

发布结构：

```text
release-web
├── latest.json
└── versions/
    └── vX.Y.Z/
        ├── web.tar.gz
        ├── web.tar.gz.sig
        └── web.tar.gz.sha256
```

客户端流程：

1. 启动时仍先加载内置 `dist`，保证离线可用。
2. 后台检查 `release-web/latest.json`。
3. 校验 `appVersionRange` 与 `requiredCapabilities`。
4. 流式下载 `web.tar.gz` 到应用数据目录。
5. 校验 sha256。
6. 用 minisign 校验签名 payload。
7. 安全解包到 staging 目录，再原子切换到版本目录。
8. 下次重启通过本地 `tuziweb://` 协议加载热更新资源。

签名 payload 固定为三行：

```text
sha256
version
appVersionRange
```

经验：不要混用 Tauri updater signer 和 minisign。它们格式不同，CI 生成与 Rust 验签必须使用同一种签名协议。

## Capability Facade v1

统一入口：

- `get_capability_manifest()`
- `invoke_capability(request)`

请求格式：

```json
{
  "id": "terminal.launchProvider",
  "version": ">=1.0.0",
  "payload": {}
}
```

响应格式：

```json
{
  "ok": true,
  "data": {}
}
```

错误格式：

```json
{
  "ok": false,
  "error": {
    "code": "unsupported_capability",
    "message": "Unsupported capability",
    "retryable": false
  }
}
```

v1 能力：

- `terminal.launchProvider`
- `terminal.launchCommand`
- `system.openUrl`
- `system.openPath`
- `config.getAppConfigInfo`
- `update.checkNative`
- `update.getWebStatus`
- `update.checkWeb`

安全边界：

- `terminal.launchProvider` 只按已有 provider/app/cwd 打开终端。
- `terminal.launchCommand` 只允许产品内声明安全的恢复类命令，例如 `codex resume ...`、`claude --resume ...`。
- `system.openUrl` 只允许 `http` 和 `https`。
- Web 热更新包必须声明并通过 `requiredCapabilities` 校验。

## CI 发布要点

tag 发布会执行：

1. 创建或复用 draft release。
2. 多平台构建安装包、updater 包和 `.sig`。
3. 上传 Release Assets。
4. 生成 `release-manifest/latest.json`。
5. 构建前端资源包，生成 sha256 和 minisign 签名。
6. 推送 `release-web` 分支。
7. purge jsDelivr cache。
8. 公开 Release。

需要配置的 secrets：

- `TAURI_SIGNING_PRIVATE_KEY`
- `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`
- `WEB_UPDATE_MINISIGN_PRIVATE_KEY`

## 验证清单

发布前至少跑：

```bash
pnpm typecheck
cd src-tauri && cargo check
cargo test capabilities
cargo test web_hot_update
ruby -e 'require "yaml"; YAML.load_file(".github/workflows/build.yml")'
git diff --check
```

发布后检查：

- `release-manifest/latest.json` 可访问。
- `release-web/latest.json` 可访问。
- manifest 包含版本、URL、sha256、signature、requiredCapabilities。
- 旧版本能检测到原生更新。
- Web 热更新下载后，下次重启生效。
- 签名错误、sha256 错误、能力缺失时不会启用热更新资源。

## 经验总结

- “无感升级”不能以牺牲执行边界为代价，桌面 App 不应执行 CDN 下发的任意脚本。
- 大安装包和小 manifest 分开托管，发布链路更稳。
- 热更新适合 UI 与业务逻辑微调，不适合 native 权限、插件、系统能力变化。
- 能力层要版本化，热更新前端只调用 manifest 中存在且满足版本范围的能力。
- CI 和客户端必须共享同一个签名协议，否则发布后才会暴露为安装失败。
