# tuzi-switch 与 cc-swicth 项目对比分析与修复方案

## 一、项目基本信息对比

### 1.1 项目版本与基本信息

| 项目名称 | 版本 | 描述 |
|---------|------|------|
| tuzi-switch | 1.1.3 | All-in-One Assistant for Claude Code, Codex & Gemini CLI - tuzi switch |
| cc-swicth | 3.16.0 | All-in-One Assistant for Claude Code, Codex & Gemini CLI |

### 1.2 项目结构对比

两个项目的整体结构非常相似，主要区别在于：

1. **命名差异**
   - `CC_SWITCH_CODEX_MODEL_PROVIDER_ID` vs `TUZI_SWITCH_CODEX_MODEL_PROVIDER_ID`
   - `CC_SWITCH_CODEX_MODEL_CATALOG_FILENAME` vs `TUZI_SWITCH_CODEX_MODEL_CATALOG_FILENAME`
   - 相关的配置注释和标识

2. **功能差异**
   - tuzi-switch 项目似乎是基于 cc-swicth 的一个分支版本
   - tuzi-switch 项目中有一些新的功能，例如 OpenCode 应用的支持

## 三、功能实现差异分析

### 3.1 OpenCode 应用支持

**tuzi-switch 项目：**
- 完整的 OpenCode 应用支持
- 包含 `useOpencodeFormState.ts` 钩子
- 包含 `opencodeFormUtils.ts` 工具
- 包含 `opencodeProviderPresets.ts` 预设配置

**cc-swicth 项目：**
- 似乎没有完整的 OpenCode 应用支持
- 相关的 API Key 验证逻辑在 `providerConfigUtils.ts` 中没有体现

### 3.2 Codex 配置升级处理

**tuzi-switch 项目：**
- 完善的 Codex CLI 版本检测
- 自动识别并处理新旧配置格式
- 在保存配置时自动清理旧版 `profile` 字段
- 在读取配置时自动迁移旧版格式

**cc-swicth 项目：**
- 没有相关的版本检测和配置升级逻辑
- 可能需要手动处理配置升级

### 3.3 API Key 验证机制

**tuzi-switch 项目：**
- `needsApiKey` 函数提供全面的 API Key 检测
- 支持 Claude、Codex、Gemini、OpenCode 等多种应用类型
- 在启用供应商前检查 API Key 是否填写

**cc-swicth 项目：**
- 没有类似的 `needsApiKey` 函数
- 没有 API Key 缺失的确认对话框

## 四、Bug 修复方案研究

### 4.1 OpenCode API Key 识别问题

#### 问题描述
用户在 OpenCode 应用中填写了 API Key，但系统仍然提示 API Key 未填写。

#### 问题根因
在 `ProviderList.tsx` 的 `needsApiKey` 函数中，缺少对 OpenCode 应用类型的处理。OpenCode 应用的 API Key 存储在 `settingsConfig.options.apiKey` 中，而不是像其他应用那样存储在 `settingsConfig.env` 中。

#### 修复方案

**文件 1：src/components/providers/ProviderList.tsx**

在 `needsApiKey` 函数中添加对 OpenCode 的支持：

```typescript
if (appId === "opencode") {
  const config = provider.settingsConfig as Record<string, unknown> | null;
  const options = config?.options as Record<string, unknown> | undefined;
  return !(
    typeof options?.apiKey === "string" &&
    String(options?.apiKey ?? "").trim()
  );
}
```

**文件 2：src/utils/providerConfigUtils.ts**

更新三个核心函数以支持 OpenCode：

```typescript
// 在 getApiKeyFromConfig 函数中添加
if (appType === "opencode") {
  // OpenCode API Key (检查 options.apiKey)
  const options = config?.options;
  if (options && typeof options === "object" && options !== null) {
    const apiKey = (options as Record<string, unknown>)?.apiKey;
    if (typeof apiKey === "string" && apiKey && !apiKey.includes("${")) {
      return apiKey;
    }
  }
}

// 在 hasApiKeyField 函数中添加
if (appType === "opencode") {
  const options = config?.options;
  return !!(options && typeof options === "object" && options !== null && 
           Object.prototype.hasOwnProperty.call(options, "apiKey"));
}

// 在 setApiKeyInConfig 函数中添加
if (appType === "opencode") {
  if (!config.options) config.options = {};
  config.options.apiKey = apiKey;
  return JSON.stringify(config, null, 2);
}
```

### 4.2 Codex 配置升级问题

#### 问题描述
Codex CLI 升级到 0.134.0+ 后，旧版的 `profile = "codex"` 配置不再被支持，会提示错误。

#### 问题根因
Codex CLI 0.134.0+ 版本改变了配置格式，不再支持顶层的 `profile` 字段，需要使用新的配置格式。

#### 修复方案

**文件 1：src/components/providers/forms/hooks/useCodexConfigState.ts**

在 `migrateLegacyConfig` 函数中添加移除旧版 `profile` 字段的逻辑：

```typescript
function migrateLegacyConfig(configStr: string): string {
  // ... 原有的迁移逻辑 ...
  
  // 移除顶层 profile = "xxx" 字段
  let result = configStr.replace(/^\s*profile\s*=\s*"[^"]+"\s*$/gm, "");
  
  // ... 继续原有逻辑，使用 result 而不是 configStr ...
}
```

**文件 2：src-tauri/src/codex_config.rs**

在 `save_route_to_config` 函数中添加移除旧版 `profile` 字段的逻辑：

```rust
// For new format (0.134.0+), remove top-level profile = "xxx" field
if new_format {
    lines.retain(|l| !l.trim().starts_with("profile = \""));
}
```
