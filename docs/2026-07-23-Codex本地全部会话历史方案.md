# Codex 本地全部会话历史方案

## 1. 目标

只处理 Codex：增加一个“一键获取全部 Codex 本地会话”能力，让用户切换或新增供应商后，仍能统一查看并恢复本机已有的 Codex 会话。

这里的“显示在 ChatGPT 中”按以下可实现范围定义：

- 在 tuzi-switch 的 Codex 会话页统一显示。
- 在 Codex 的本地 Resume 历史中统一显示并可继续会话。

不包含把本地历史上传或注入官方 ChatGPT 网页、桌面端云端侧边栏；目前没有受支持的批量导入接口。

## 2. 现有能力

项目已经具备主要基础：

- 扫描 Codex `sessions` 和 `archived_sessions` 下的 JSONL 会话。
- 从 `session_index.jsonl` 和 `state_5.sqlite` 补全会话标题。
- 支持默认目录、自定义 Codex 配置目录、`sqlite_home` 和 `CODEX_SQLITE_HOME`。
- 将历史 JSONL 的 `model_provider` 和 SQLite `threads.model_provider` 统一迁移到稳定的 `tuziswitch` 历史桶。
- 迁移前备份，并使用迁移账本支持精确恢复。
- 会话页已支持列表、元数据搜索、消息查看、复制 Resume 命令和删除。

因此无需新建一套历史存储，只需把现有能力整理为明确的一键入口，并补齐扫描结果与性能边界。

## 3. 推荐设计

### 3.1 Codex 会话页新增“一键获取全部历史”

在 Codex 会话页增加主按钮：

> 获取全部 Codex 本地会话

点击后执行：

1. 只读扫描所有 Codex 活动与归档会话目录。
2. 扫描所有候选 `state_5.sqlite` 和 `session_index.jsonl`。
3. 汇总当前已经可见、分散在旧供应商桶、仅有 SQLite 元数据的会话。
4. 展示扫描预览，不立即改写文件。
5. 如果存在分散历史，用户确认后统一迁移到 `tuziswitch` 历史桶。
6. 刷新 Codex 会话列表，并显示迁移与跳过结果。

### 3.2 扫描预览

确认弹窗展示：

- 本地发现的 Codex 会话总数。
- 活动会话数与归档会话数。
- 已在统一历史桶中的数量。
- 需要迁移的旧供应商历史数量。
- 仅存在 SQLite 元数据、缺少 JSONL 正文的数量。
- 无权限、损坏或解析失败的文件数量。
- 本次备份位置与预计改写文件数。

普通扫描必须只读；只有用户确认“统一并显示”后才执行迁移。

### 3.3 迁移规则

- 目标历史桶固定为 `tuziswitch`，不随当前供应商 ID 改变。
- JSONL 只修改 `session_meta.payload.model_provider`，其他内容保持原样。
- SQLite 只更新对应 `threads.model_provider`，不改写消息正文。
- JSONL 使用逐行流式读取与临时文件原子替换。
- SQLite 使用事务、`busy_timeout` 和分块更新。
- 每次改写前创建备份并更新迁移账本。
- 重复点击必须幂等：已经统一的历史直接跳过。
- 单个文件失败不能阻断其他文件，但最终必须明确显示失败项。

### 3.4 展示与恢复

迁移完成后：

- tuzi-switch 的 Codex 会话页展示全部可读取历史。
- Codex Resume 按统一的 `tuziswitch` 桶读取历史。
- 活动与归档会话都可查看。
- 仍保留原会话 ID、时间、项目目录与 Resume 命令。
- 仅有 SQLite 元数据但缺少 JSONL 的 thread 标记为“正文文件缺失”，不可伪造或恢复消息。

### 3.5 关闭与恢复

设置中保留现有“统一 Codex 会话历史”开关：

- 关闭开关时不自动粗暴回迁全部 `tuziswitch` 会话。
- 用户可选择按备份账本恢复本次迁入的官方历史。
- 开启统一期间新产生的会话来源无法可靠反推，默认不回迁。

## 4. 建议接口

尽量复用现有模块，只增加必要接口：

- `preview_codex_history_unification()`：只读扫描并返回预览。
- `unify_all_codex_history()`：确认后执行备份与迁移。
- `get_codex_history_operation_status()`：返回进度及分项结果。
- `cancel_codex_history_operation()`：安全取消尚未开始改写的扫描阶段。

返回结果建议包含：

- `totalSessions`
- `activeSessions`
- `archivedSessions`
- `alreadyUnified`
- `pendingMigration`
- `metadataOnly`
- `migratedJsonlFiles`
- `migratedStateRows`
- `skippedFiles`
- `issues`

不创建新的历史数据库；扫描状态只保留轻量内存数据并设置生命周期上限。

## 5. 性能与安全要求

- 不一次性读取全部 JSONL 正文。
- 扫描元数据优先读取必要行，避免解析完整会话。
- JSONL 改写必须逐行流式处理，限制单行最大长度。
- SQLite 查询只取需要的字段并分页，不执行无限制 `SELECT *`。
- 限制扫描与迁移并发，避免磁盘、内存和交换分区瞬时增长。
- 前端只展示进度与统计，不能把全部会话正文一次传入 IPC。
- 路径必须限制在解析出的 Codex 配置根和 SQLite 候选路径内。
- 默认不上传、不删除会话、不修改非 Codex 文件。
- Codex 正在写入文件时，使用锁、快照或重试机制，不能覆盖并发新增内容。

## 6. 实施步骤

### P0：一键入口与预览

- Codex 会话页增加“获取全部本地会话”。
- 后端增加只读扫描预览和问题统计。
- 明确区分活动、归档、待迁移、仅元数据及失败记录。

### P1：统一迁移闭环

- 复用现有历史迁移与备份账本。
- 支持一次确认后统一全部已知旧供应商桶。
- 增加进度、幂等、部分失败重试和结果提示。
- 完成后刷新会话列表并提示重新打开 Codex Resume。

### P2：大历史优化

- Codex 会话列表改为游标分页。
- 单会话消息按段加载，避免完整 `Vec` 经过 IPC。
- 增加扫描取消、缓存字节上限和过期清理。

## 7. 验收标准

- 用户只需在 Codex 会话页点击一次，即可发现默认目录、自定义目录中的全部活动和归档会话。
- 新增或切换 Codex 供应商后，统一过的历史仍在 tuzi-switch 和 Codex Resume 中可见。
- JSONL 与 SQLite 的 `model_provider` 结果一致。
- 重复执行不会重复备份或反复改写已统一文件。
- 文件损坏、权限不足和 SQLite 忙碌均有明确结果，不会静默漏历史。
- 仅有 SQLite 元数据的 thread 可以被识别，但不会被误报为具有完整正文。
- 扫描和迁移过程中内存有上限，不把所有会话正文载入内存。
- 迁移失败时原始文件仍可恢复，不产生截断 JSONL 或损坏 SQLite。

## 8. 推荐结论

推荐实施 **P0 + P1**。现有项目已经完成 Codex 扫描、历史桶统一、备份和恢复的主体能力，新增工作主要是把它们组合成用户可理解、可预览、可重试的一键流程。

P2 在本地历史规模较大时再实施，但迁移读写从一开始就必须保持流式与分块处理。
