4. live 配置验证：确认 `config.toml` 顶层为 `model_provider = "tuziswitch"`，且存在 `[model_providers.tuziswitch]`。
5. 应用模板验证：确认当前 Codex provider 的 `settings_config.config` 也已同步为 `model_provider = "tuziswitch"`。
6. 主 state DB 验证：`~/.codex/state_5.sqlite` 中旧 `provider-coding01`、`provider-coding02`、`tuzi`、`codex` 已归并到 `tuziswitch`。

## 建议人工验证

1. 清空或删除两个 Codex 应用增强字段后打开设置页，确认两个开关默认开启。
2. 手动关闭两个开关并保存，刷新设置页后确认恢复开启。
3. 再次手动开启两个开关，确认仍可正常保存。
4. 切换到 Codex 第三方供应商后，检查 `auth.json` 仍保留官方登录材料。
5. 打开 Codex，新建一条会话，确认新 thread 的 `model_provider` 为 `tuziswitch`。
6. 在 Codex resume history 中确认旧第三方历史和新会话可在同一历史桶下出现。
7. 重启 `tuzi-switch`，确认 `config.toml` 不会从 `tuziswitch` 回退到旧 `provider-*`。

## 回归关注

- 不应清空 `auth.json` 中的官方登录材料。
- 不应把用户手动关闭保存成持久 `false`，刷新或重启后应恢复开启。
- 不应默认迁入既有官方会话，迁入仍需用户确认。
- 不应把未知外部 provider id 粗暴迁入 `tuziswitch`，迁移源必须来自本机 tuzi-switch Codex provider 配置。
- 不应重复迁移已统一的 state DB。
- 不应在关闭统一历史时把所有 `tuziswitch` 会话粗暴改回 `openai`，只能按备份账本恢复官方会话。
- state DB 备份必须在改写前完成，且要保留 `sqlite/` 子目录路径，避免两个 `state_5.sqlite` 备份互相覆盖。
